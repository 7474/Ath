# アーヴ語翻訳のアーキテクチャ

この文書は、`baronh` パッケージと `web/` の翻訳・音声が、何を保証し何を捨てているかを記録する。CLI（`python3 -m baronh`）とブラウザ（`web/js/engine.js`）は同じ方針で動く。

公式の完全辞書は公開されていない。文法の骨格は Wikipedia「[アーヴ語](https://ja.wikipedia.org/wiki/%E3%82%A2%E3%83%BC%E3%83%B4%E8%AA%9E)」（CC BY-SA）、語彙はファンによる再構成を走査した二次資料である。訳は再構成であり誤りを含む。

## 目的

- 既定はローカル完結。辞書と文法規則だけで ja / en / baronh を翻訳し、読み上げまで行う。Web ではアーヴ語を選んだ入出力欄だけアース文字フォントで表示する。
- 生成 AI は任意。OpenAI Chat Completions 互換のエンドポイントがあれば使える。無くても翻訳は動く。
- 生成 AI を使うときも、辞書全文と文法全書は 1 回の API 呼び出しに載せない。
- モデルが造語した普通名詞を、そのままアーヴ語として出さない。

## 全体構成

```
入力（ja / en / baronh）
        │
        ▼
  規則ベース翻訳（辞書 lookup + 格変化 / 動詞活用）
        │
        ├── 既定: この訳を採用
        └── --engine openai / Web の「生成AI」
               ① 下訳・解析・未登録語を作る（ローカル）
               ② 辞書を全件スキャンし、関連見出しだけを渡す
               ③ Chat Completions（必要なら lookup_lexicon を queries 一括で 1 往復）
               ④ 生成したアーヴ語を辞書語形と照合。造語なら再生成、なお悪ければ下訳
        │
        ▼
  Ath キーと仮名読みはローカルで再計算
        │
        ▼
  読み上げ（別経路。翻訳 API は音声を返さない）
        ├── ローカル: 仮名 → espeak-ng / Web Speech（ja-JP）
        └── 生成エンジン選択時: 同じベース URL の /audio/speech
               失敗したらローカル読み上げに戻る
```

実装の対応は次のとおり。

| 役割 | Python | ブラウザ |
|---|---|---|
| 規則翻訳 | `baronh/translate.py` | `web/js/engine.js` の `translate` |
| 辞書・点数付け | `baronh/lexicon.py` | 同ファイルの `Lexicon.rank` / `search` |
| 生成 AI | `baronh/openai_backend.py` | `web/js/app.js` が Chat Completions を呼ぶ |
| 格・活用 | `baronh/grammar.py` | `web/js/engine.js` |
| 発音転記・読み | `baronh/phonology.py` | `web/js/engine.js` |

## 規則ベース（既定）

辞書見出しと日本語・英語語釈の照合、7 格、動詞活用、主題 `F'a`、疑問の `sa` などを規則で組む。生成 AI がオフでもこれが最終訳になる。

辞書にないカタカナ名・欧文の固有名詞は、日本語ローマ字ではなくアーヴ語の正書法へ発音転記する。アースに無い `j/k/w/v` は使わず、ジ行は `gh`、カ行は `c`、ヴは `bh`。語幹が母音で終われば第3型の主格 `-c`、子音なら第2型 `-h`（既に `-n` なら第1型系）を付け、格変化する。解析と注記で「辞書の見出しではない」と示す。普通名詞の未登録は原文の語を残す。

日本語の部分一致 lookup は、CJK / 仮名クエリでは行わない。`ジント` が `サイ・ジント様` に吸われるのを避けるためである。

## 生成 AI（任意）

### なぜベクトル RAG ではないか

マージ後の辞書は約 2400 見出しで、lemma / 日本語 / 英語で引ける表である。全文を整形すると約 16 万文字になり、1 プロンプトに載せる量ではない。一方、件数は線形スキャンで足りる。

埋め込みの近似検索は、語釈の部分一致や固有名詞の包含で誤爆しやすい。この辞書では、見出しと語釈の照合の方が誤りが少ない。モデルが足りない語を能動的に引く、という役割はツール呼び出しが担う。

### 呼び出しの流れ

1. 先に規則ベースで下訳と解析トークンを作る。下訳は誤り・抜けがあり得る、とプロンプトに書く。
2. 原文・下訳・解析からトークンを取り、辞書を全件スキャンして点数付けする。上位のみ（既定最大 36、実際はそれより少ない）を関連辞書として渡す。
3. システムプロンプトに文法要点、格・動詞などの詳細トピック、数件の例示を載せる。
4. `POST {base}/chat/completions`。モデルは `lookup_lexicon` と `grammar_note` を呼べるが、足りない語は `queries` / `topics` 配列にまとめて **1 往復で** 引く。ツールを実行したら次の呼び出しは `tool_choice=none` とし、1 語ずつの連続呼び出しは切る。ツール非対応（400 など）ならツールなしの単発に切り替える。
5. 生成が空なら下訳を使う。アーヴ語の Ath キーと仮名読みは、生成文をローカルで再計算する。解析行は規則ベースのまま残す。

原文そのものは常にユーザメッセージに入る。検索が外れても、モデルは原文を読める。

### 検索（関連語の渡し方）

`Lexicon.rank` / `score_entry`（`baronh/lexicon.py`）が全文スキャンする。完全一致の語釈・見出しを強くし、弱い部分一致は採らない。しきい値未満は渡さない。

ツール `lookup_lexicon` は同じ点数付けを、`queries` 配列の各語に対して一度に行う。旧来の単一 `query` も受け付けるが、スキーマ上の必須は配列である。`grammar_note` は `cases` / `verbs` / `pronouns` / `syntax` / `phonology` の定型テキストを `topics` 配列でまとめて返す。文法トピックはシステムプロンプトに既出なので、通常は呼ばない。

ファジー照合は原文トークンに対してだけ行う。下訳の語形（例: `bale`）を 1 文字差で別見出し（例: `bate`「待つ」）に結ばない。

### 残すファジー / 捨てるファジー

生成 AI の誤字耐性（原文を読んで意図を補う力）は捨てない。捨てるのは、意味が近そうな別語を広く拾う検索である。

| 残す | 捨てる |
|---|---|
| 原文をプロンプトに載せる（モデルが誤字を読める） | 埋め込みベクトルによる意味検索 |
| ひらがな/カタカナ、ヴ/ブ、長音、NFKC の畳み込み（`アーブ` / `あーヴ` → `abh`） | 日本語の部分一致（`ジント` ⊂ `サイ・ジント様`） |
| ラテン綴りの編集距離 1 かつ折りたたみ後 4 文字以上（`usare` → `usere`） | 日本語同士の 1 文字差（`ジントは` と `ジント様` を結ぶ） |
| ます/する など活用語尾を剥がした語釈照合 | 下訳トークンに対するタイポ照合 |
| 辞書に近い表記ゆれは、発音転記より辞書見出しを優先するよう注記する | 漢字の当て字（`わかります` と `分かります`）の自動同一視 |

畳み込みと 1 文字差は「同じ語の表記ゆれ」向けである。意味の近い別語を探す処理ではない。

漢字の当て字は検索では見ない。そこは原文を読んだモデル側に任せ、見つかった見出しだけで訳させる。

### プロンプトに載せるもの / 載せないもの

載せる: 短い文法要点、文法トピック全文（数百文字）、数件の例示、規則下訳、関連辞書の上位、未登録・発音転記・表記ゆれの注記。

載せない: 辞書全文、文法の書籍相当、ベクトル索引。

### 生成後の検証

目標言語が baronh のとき、生成文を語形インデックス（`FormIndex`）で照合する。

- 後置詞 `a` `sa` や `F'a` などは閉集合として許可する。
- 規則側が発音転記した固有名詞の語形は許可する。
- 原文のまま残した CJK は許可する（造語せず残す方針）。
- それ以外のラテン語で辞書語形に無いものは造語とみなす。

造語があれば一度書き直しを求め、改善すればそれを採用する。なお多い場合は規則下訳に戻す。検証は「辞書にある語形か」であり、「関連辞書に載った語だけか」ではない。モデルが原文から正しく `abh` を思い出して `bale` と書けば通る。

### 音声合成

翻訳の Chat Completions は音声を返さない。読み上げは別呼び出しである。

アーヴ語は先にローカルで仮名読みにする。クラウド TTS はアーヴ語の読みを知らないため、ローマ字のまま渡さない。エンドポイントは `{base}/audio/speech`。未対応なら espeak-ng または `speechSynthesis`（ja-JP）に戻る。Web で TTS モデル欄を空にするとクラウド TTS は呼ばない。

### 互換 API

既定ベース URL は `https://api.openai.com/v1`。ホストだけ書くと `/v1` を付ける。LM Studio / vLLM / LiteLLM / Ollama の OpenAI 互換口など、Chat Completions と同じ形なら使える。

- CLI: `--api-base` / `--api-key` / `--model` / `--tts-model`
- 環境変数: `OPENAI_BASE_URL` または `OPENAI_API_BASE`、キーは `OPENAI_API_KEY`
- Web: `localStorage`（`ath-translate.openai-base` など）

`api.openai.com` 以外ではキー空でも `Bearer no-key` を送る（ローカル互換向け）。チャットモデルと TTS モデルは別指定である。多くのローカル互換は `/audio/speech` を持たない。

## 制約と既知の限界

- 公式辞書が無い。未登録の普通名詞（例: 「光」）は、生成 AI でも造語せず原文の語を残す。品質の上限は辞書の被覆で決まる。
- 二次資料の語釈は編者の再構成であり、森岡浩之氏は関知していない。
- 小さいローカルモデルはツールを呼ばず下訳をなぞることがある。ツール非対応なら単発に落とす。
- 規則ベースの下訳自体の誤り（活用の重複など）は、モデルが見直せば直るが、必ず直る保証はない。
- 生成エンジンでも解析ハイライトは規則ベースのトークン分割である。最終訳と解析行が一致しないことがある。
- ベクトル RAG を足しても、辞書に無い概念は埋まらない。効くのは辞書の拡充と、照合の精度である。

## 設定を変えても変わらないこと

次は実装の前提であり、API ベース URL やモデル名では変わらない。

- 辞書全文をプロンプトに載せない。
- 日本語 CJK の部分一致 lookup をしない。
- 翻訳と TTS を同じ HTTP 呼び出しにまとめない。
- アーヴ語 TTS の入力は仮名読みである。
- Ath キーと読みはサーバではなくローカルで計算する。
